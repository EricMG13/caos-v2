# Vendor change request — let `parse_t8` accept the CP-DR row CP-0's own contract asks for

**Date:** 18 September 2026. **Status:** answered by build `6a5f1050`
(`docs/DECISIONS.md` §96, `docs/VENDOR_CHANGES.md`), under the owner's
approval of 18 September 2026 to alter vendor files with a record. Found by
Completion Phase 9 Task 9.4 while writing the whole-route test for
`LITE_CREDIT_22 / LITE_DEEP_RESEARCH`, which stopped rather than build a host
reading the bundle refuses.

**Asks for:** the bundle's `credit_os_v/navigation.py::parse_t8` to accept a
T8 row naming `CP-DR`, as the same bundle's `validate_catalog`, CP-0's
`SKILL.md` and the vendor's own `plan_from_cp0` already expect it to.

**Unblocks:** the `DEEP_RESEARCH` and `LITE_DEEP_RESEARCH` pathways, whose
only consumer is CP-DR, and with them Completion Phase 9 Task 9.4 step 4 (the
route test and its enablement) and step 7 (the live run); and the host's route
extension (§6), which appends CP-DR to another pathway and would then need
the same row.

## What the bundle says three times and refuses once

1. `CREDIT_OS_V_MODULE_CATALOG_v2.json` declares CP-DR `navigable: true` with
   `layer_id: null`, and `validate_catalog` (navigation.py, the `if
   navigable:` branch) admits exactly that combination for CP-DR alone:
   `if not (module_id == "CP-DR" and layer_id is None) and (...)`.
2. `cp-0-source-readiness/SKILL.md`, "T8 recommended-run command contract":
   "T8 contains only canonical live, navigable host module IDs: CP-1, …,
   CP-L10, CP-DR." And "Research activation — CP-DR": "Recommend it in T8
   only with a concrete question and receiving module."
3. `plan_from_cp0` handles CP-DR rows in the recommendation list -- it appends
   one when a brief is present and none was written, and `render_layer` has a
   branch for `row.module_id == "CP-DR"`.
4. `parse_t8` refuses the row:
   `if module is None or not module.navigable or module.layer_id is None:
   raise NavigationError("CP-0 recommends unknown or non-navigable module")`.
   CP-DR's `layer_id` is null, so every CP-DR row is refused. `parse_t8` runs
   first in `plan_from_cp0`, before the brief is read, so the append in (3)
   is never reached for a CP-0 that did what (2) told it to.

An empty T8 is refused too ("CP-0 T8 has no navigable recommendation rows"),
and CP-0's T8 register declares `minimum_body_rows: 1`. So on a pathway whose
node list is CP-0 and CP-DR, no T8 the bundle accepts exists: a CP-DR row is
refused, an empty table is refused, and any other module is outside the
selected pathway (`Route` refuses "CP-0 plan contains modules outside the
selected pathway"). The pathway is dead as authored, in the bundle's own
code. `vendor/deploy-v/tests/` never drives a DEEP_RESEARCH CP-0, which is
how it has stayed so.

Until the change below landed, the host pinned all of this mechanically in a
test that failed the day the parser changed. It is now
`tests/test_bundle_pin.py::test_the_t8_parser_accepts_the_cp_dr_row_cp0s_contract_permits`,
which holds the answer instead.

## Why the host will not work around it

Invariant 4: the bundle is the methodology authority and the host adds no
rule. Every workaround is a host reading the bundle refuses:

- **Skip `parse_t8` when the gate expects only CP-DR.** The host would be
  validating CP-0 by a different rule than the bundle's on one pathway, and
  CP-0's `completeness_check` would still require a T8 row that nothing may
  fill.
- **Take CP-DR's readiness from the brief instead of from T8.** That is what
  `plan_from_cp0` does *after* `parse_t8` has passed, and it does not save the
  pathway: the parser still refuses the table before it. On the host it would
  also be a second reading of readiness beside `route._state_for`, which the
  ledger's "Canonical upstream refs do not read readiness" entry already
  declines.
- **Let CP-0 name a module outside the pathway so T8 is non-empty.** Refused by
  the vendor's `Route` and by the host's `_readiness` (the T8 module set must
  equal the pinned consumers).

## The change

One condition in `parse_t8`, the same exemption `validate_catalog` already
makes:

```python
if module is None or not module.navigable or (
    module.layer_id is None and module_id != "CP-DR"
):
```

Nothing else moves: `Recommendation` is unchanged, the row's columns are
unchanged, `plan_from_cp0`'s append-when-absent and refuse-without-a-brief
branches keep their meaning, and a CP-0 that never mentions CP-DR is read
exactly as before. The vendor test that should accompany it is a DEEP_RESEARCH
scenario in `test_module_workflow.py`: a CP-0 whose T8 names CP-DR alone, a
brief in the snapshot, `prepare(... module_id="CP-DR")` succeeding.

## How it was answered

Exactly the one condition above, in the vendored
`credit_os_v/navigation.py`, and the vendor test this request asked for:
`test_research_workflow.py::test_deep_research_pathway_recommends_cp_dr_alone`
(a `FULL_CREDIT_32 / DEEP_RESEARCH` CP-0 whose T8 names CP-DR alone, a brief
in the snapshot, `prepare(... module_id="CP-DR")` succeeding and the authored
dossier completing the pathway). `verify_package.py --refresh` regenerated
the metadata; the authority digest did not move, because `navigation.py` is
not a pinned authority component. With the parser answered, the host enabled
`LITE_CREDIT_22 / LITE_DEEP_RESEARCH` behind its whole-route test
(`tests/test_lite_deep_research_route.py`).
