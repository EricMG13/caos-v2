## The gap, stated exactly

`server/methodology/invocation.py`'s `host_identity` names every accepted direct
input and refuses a blocking one that is missing, which is what the vendor's
`expected_upstream_digests` does. It omits one of the vendor's inputs: **a soft
edge whose source is unaccepted but which CP-0 reported READY.** The vendor
refuses such a node; the host does not ask.

Today that costs nothing, and the brief must not pretend otherwise. The route
engine BLOCKS a node whose soft upstream is unaccepted-and-READY before the
runtime ever asks for its identity, so the two disagree only in a state the
engine does not produce. What makes it worth closing is that the engine's rule
and the identity builder's rule are stated in different places and neither cites
the other: the day `node_states` changes — and Phase 10's per-node evidence
selection is exactly such a change — the identity builder silently stops
matching the vendor.

## Contract and scope

1. **Read the readiness the runtime already has.** Slice c-5b added a canonical
   CP-0 T8 reader to the runtime and d-2 to the proof; `accepted_artifacts`
   reduces each row to a typed `route.NodeResult` carrying the readiness rows.
   `host_identity` must take that same reading rather than re-deriving one: a
   second reader of the same artifact is a second authority, and invariant 3
   says there is one.
2. **Join it to the refs.** A soft edge whose source is unaccepted and whose
   CP-0 readiness is READY joins `upstream` as a ref the way a blocking edge
   does, so the digest the record binds names it. A soft edge whose source is
   unaccepted and not READY stays omitted, as now.
3. **Refuse the disagreement rather than paper over it.** If the engine would
   run a node the vendor's rule would refuse, that is `ROUTE_IDENTITY_INVALID`
   before any attempt — the same code and the same place the missing-blocking-
   upstream case already refuses. Do not invent a new code, and do not let the
   host proceed on a reading the bundle contradicts (invariant 4).
4. **Do not touch the anchor.** `module_name` is still read from the verified
   catalog at call time and the anchor is still derived from the CP-0 ref. Both
   stay in the ledger entry with their own upgrade.

## RED-first acceptance checks

Each is watched failing for the stated reason before the code exists.

- `test_a_ready_soft_upstream_joins_the_refs_even_though_it_is_unaccepted` — a
  route with a soft edge whose source CP-0 marked READY and which accepted
  nothing; the consumer's `HostIdentity` names it.
- `test_an_unready_soft_upstream_is_still_omitted` — the same route with the
  readiness anything but READY; the ref is absent. This is the pair that shows
  the rule reads readiness rather than just adding every soft edge.
- `test_a_node_the_engine_would_run_and_the_vendor_would_refuse_is_refused` —
  the disagreement, refused `ROUTE_IDENTITY_INVALID` with no attempt,
  reservation or call.
- `test_the_record_binds_the_ready_soft_upstream` — the digest moves, which is
  what makes this worth doing: a record that did not name the input cannot be
  re-checked against it.
- The existing identity and freshness suites stay green unchanged; if one moves,
  say which and why in the report rather than editing it quietly.
