the smallest catalog pathway that contains every owner and every required

the route runs. The complementary plan named `FULL_CREDIT_ASSESSMENT`; REPAIR_PLAN
asks only for "a catalog route containing CP-1, CP-2G and CP-4", and 17 unproven
modules would be speculative scope. `FULL_CREDIT_ASSESSMENT` stays disabled.

## Decisions

1. **Enable per module, then per route.** A module joins `ADAPTER_MODULES` only
   in the slice that proves its contract; `(FULL_CREDIT_32, RELATIVE_VALUE)`
   joins `ADAPTER_ROUTES` only in the last slice, after the whole-route proof.
   Every other pathway stays refused `HANDOFF_MODULE_UNSUPPORTED`.
2. **One generic realistic fixture builder.** Generalise the LITE builder into
   `tests/canonical_route_fixtures.py`: registers and minimum rows from
   `load_contract`, host front matter from the prompt, citations quoting whole
   tokens of one realistic issuer pack (annual report extract with the figures
   CP-1 records, a facility agreement extract with the covenant terms CP-4
   records, a peer table for CP-1C). Module-specific cell content lives in one
   small function per module; nothing reads the code under test.
3. **Per-module contract proof (the Phase 3 standard).** For each new module:
   vendor validation of the exact Markdown; host identity including every
   direct upstream ref; projections read back from the record; every citation
   anchored in delivered blocks; a `Restricted` handoff keeps its limitations;
   a missing required register, a wrong upstream digest and an unanchored quote
   each refuse with their existing codes.
4. **CP-2G's drivers are data CP-CF will read.** The
   `cp2g.cp_model_forecast_drivers` rows in the fixture use the Task 5.1 driver
   vocabulary (`case`, `period_id`, movement names, `status`) so 5.2b can map
   them without inventing fields; a test pins the column set against the vendor
   contract and records any mismatch as a 5.2b input rather than editing the
   vendor.
5. **Whole-route deterministic run.** A `RELATIVE_VALUE` run through the real
   runtime and a deterministic provider completes all nine nodes, proves
   (`assert_orchestration_proof`) and freezes a canonical deliverable; each
   request fits `MAX_REQUEST_BYTES`.
6. **Optional and advisory edges** keep the route engine's existing semantics;
   the run proves CP-3 accepts with its OPTIONAL CP-1C/CP-2G/CP-3D inputs
   present and records the engine's behaviour when an OPTIONAL input is absent.
