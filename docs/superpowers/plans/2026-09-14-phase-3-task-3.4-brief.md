# Phase 3 Task 3.4 — prove the single LITE route end to end (binding brief)

- **Base:** the Task 3.3 acceptance tip (slices 3.4b onward start only after it;
  3.4a, a new test-only fixture module, may start earlier).
- **Authority:** `docs/REPAIR_PLAN.md` Phase 3 items 5 (remainder) and 6, exit
  checks, guardrails; complementary plan Task 3.4, Shared Phase Entry/Exit and
  Model routing; Task 3.1–3.3 briefs (process change applies);
  `docs/DECISIONS.md` §39, §41–§46; `docs/CI_GATE_CONTRACT.md`.

## Scope

1. Realistic handoffs derived from verified vendor contracts, driven through
   `run_route` → runner → executor → validator → proof → deliverable on the
   catalog route.
2. Malformed, Blocked, wrong-upstream, undelivered-citation, truncated and
   injected CP-L10 results never become usable analysis for CP-5.
3. Restricted keeps limitations everywhere; conflicts preserved; neither is QA
   clearance.
4. CP-5 runs its full workflow over the named object
   `lite_financial_change_screen` (§46.1).
5. Read-model labels in the deliverable (§45.6, §46.3).
6. `docs/PHASE_3_EXIT_EVIDENCE.md`, then the phase exit.

**Non-scope:** other routes; API response models (Phase 4); worker; paid calls;
retrieval/per-node evidence selection (Phase 5); host enforcement of vendor
rules with no vendor code.

## Gaps after 3.1–3.3

- No runtime test with realistic upstream content; fixtures fill every cell with
  `Recorded source p1`, no canonical topic ids, no conflict rows, CP-5 T5.1 does
  not name its upstream handoffs.
- No test that a Blocked, malformed or truncated CP-L10 stops CP-5, the proof and
  the deliverable.
- Restricted limitations and disclosed conflicts not proven through runtime into
  the deliverable.
- The prompt never names `owned_object`; CP-5 is called when CP-L10 is
  gate-blocked (soft ADVISORY edge).
